# Session 2026-05-25 — TX investigation findings

What we learned today (mostly the hard way). The big picture: **TX works,
DUPs are the real problem, and we lost half the day to a build-pipeline
bug.**

## Major finding #1 — TX path is functional, was masked

Once the build pipeline was fixed (see #4 below) and the first REAL test
of the current driver ran, 3 back-to-back 50-ping bursts gave:

| Run | Loss | DUPs |
|---|---|---|
| RUN1 (post-boot) | 26 % | 2  |
| RUN2 (+10 s)    | 16 % | 95 |
| RUN3 (+45 s)    |  4 % | 158 |

48 of 50 echoes returned in RUN3 with each one duplicated ~3×. Earlier
"degradation" wasn't TX failing — packets ARE reaching the host, the
switch starts flooding the reply to multiple egress paths so the host
sees the same seq number multiple times. The "26 % loss in RUN1" was an
ARP/discovery artifact + low DUP-count masking that flooding hadn't
warmed up yet.

The implication: keep working on TX correctness, but the loss number is
no longer the primary metric. **DUPs are.**

## Major finding #2 — DUPs are switch-flood, not driver bug

`refs/zte-block-diagram-from-user.png` (the diagram the user shared)
confirms the chip topology:

- **SW** block has **5 MAC ports**: MAC0 (GMII gigabit), MAC1..3 (MII
  fast-eth) → 4 GEPHY → 4 RJ45 jacks; MAC4 RGMII out to something else.
- **PP** sits between PON_MAC and SW and is what our driver writes
  registers into.
- The CPU reaches the network via PP_AXI (and SW_AXI for the SW block).
- MDIO bus on the side manages the GEPHYs (link-state, autoneg) — we do
  almost nothing with MDIO right now.

Without a populated MAC FDB in SW, the switch floods every reply we
emit from the CPU port to all 4 LAN ports + presumably MAC4 RGMII. Host
sees the frame on its single cable; the multiple-egress hairpin or
bouncebacks to CPU multiplied by the LOOPBACK-drop logic produce the
DUP count growth over time.

Fix path (still pending): populate the **sbrag MAC FDB** (the table the
switch egress actually consults — round-2 review identified `zx_fdb_add`
writes to a different VLAN-membership table). Function `sbrg_add_mactable`
is decoded at `decomp_all_tm.c:10706` and uses an indirect protocol via
`sbragRegTable` reg-IDs 0x13 CMD / 0x14 BUSY / 0x4c..0x4e DATA0..2.

## Major finding #3 — SBRAG register window is NOT at fpga_base+0x388814

Per `zx-fpga-reg-tables.h` and stock decomp, `sbragRegTable[0x13]` has
`base_dword=0x0e2005`, so the assumption was `fpga_base + 0x0e2005*4 =
fpga_base + 0x388814`. Testing this:

- A `zx_sbrag_add_mac(self_mac, vlan=0, port=1)` write at probe time =
  **immediate 100 % loss** in next test (device watchdog rebooted into
  stock NAND).
- Even a *read-only* probe (`readl` of CMD/BUSY/D0..D2 at those addresses
  in probe) wedged the **PP block silently** — kernel booted normally
  but `napi=0 irq=0` afterwards (no TM IRQs fire → no RX → 100 % loss).

So `fpga_base + 0x388814` is NOT the sbrag CMD register on our base. The
stock `fpga_base` virtual address (`pon = 0xf4000000` in
`decomp_all_zx_ponreg.c`) maps a different physical region than what our
DTS exposes as the ethernet `reg = <0x921c0000 0x200000>`. We need
either:
- a different DTS region for sbrag (perhaps `0x92xx0000` for some xx),
- or stock kotrace of `tmOnuRegWrite` to capture the *physical* address
  it actually pokes,
- or a sysfs-driven scan over the 4 MiB ioremap window for a register
  that responds with the expected `sbragRegTable[0x14]` BUSY=1 pattern.

## Major finding #4 — build pipeline silently dropped every change

`CONFIG_ZX279128_ETH=m` (module). The `.ko` ships inside the embedded
initramfs whose source is `CONFIG_INITRAMFS_SOURCE=/tmp/initramfs_extract`.
**`make zImage` did not detect changes to the driver `.c` file** —
zImage rebuilt instantly with the stale `.ko` re-embedded.

Result: roughly 1.5 hours of "edit → make → boot → test" cycles tested
the **same kernel from 05:19 over and over**. Every "regression" /
"improvement" reading from those tests is therefore invalid. The
results that did matter (the RUN1/2/3 above) only became visible after
the fix.

The fix is in `tasks/00.01.eth-driver/scripts/build_slotA.py` step 0:
detect stale `.ko`, rebuild it, copy to `/tmp/initramfs_extract/lib/modules/`,
re-make zImage. Documented inline in the script.

## Major finding #5 — boot script DTR was unreliable over TCP

`tasks/00.01.eth-driver/scripts/tftp_boot_mainline.py` used to do:
1. client-side `ser.dtr=True` → `time.sleep(2)` → `ser.dtr=False` via
   the TCP wrapper. Race-prone over TCP; the bridge sometimes didn't
   actually flip the line.
2. Fixed 120 s sleep after the `tftp` command before sending `bootm`.
   Too short if the U-Boot first attempt retransmits (cable just-up
   PHY-negotiating), too long otherwise. `bootm` could land in the
   middle of an unfinished TFTP and get swallowed.

Both fixed:
- Atomic DTR via the bridge's ctl port (`DTR_HIGH\n` → sleep 2 s →
  `DTR_LOW\n`). One round-trip per state change, no per-character
  marshalling.
- `wait_for_marker("Bytes transferred", timeout=300)` instead of a
  fixed sleep.

Doc updated in `docs/ITERATE.md` step 4.

## What works in the current driver (verified today)

- TX path delivers frames to host (RUN3 above).
- bp_idx 10-bit decode `(desc[7]>>1) | (desc[8]<<7)` is correct per
  stock decomp `pon_tm_net_poll` line 8754. The prior 7-bit decode was
  feeding all-zero buffers to the IP stack when bp_idx >= 128.
- BMU credit-refill formula `(tm[0x80dc] >> 3) & 0x3f` (was wrongly
  `>> 8`) — proved in stock decomp `pp_bmu_free_bp` L5842 via
  `(uint)(v << 23) >> 26`.
- Periodic STATS dump (`zx_bmu_dump_fn`, 5 s tick after sw_open) lands
  in `/tmp/uart_bridge.log` and gives us delta-counter visibility
  across ping runs.

## What's NOT working / open

- `zx_bmu_free_bp` call site removed: stock decomp adds it after every
  consumed RX, but our test showed HW counters with RLS > ALLOC →
  explicit free was a double-free → 100 % loss. The function code is
  kept; the call is gated. Likely stock only calls it on the PON RX
  path, not the LAN RX path we exercise.
- `zx_sbrag_add_mac`: code is correct per stock, but register window
  address is wrong (#3 above) so the function is currently dead code.
- TM IRQs sometimes vanish mid-session (we saw `napi=0 irq=0` while
  device was reachable but ping 100 %). Cause unknown — possibly the
  same flood that produces DUPs eventually saturates the desc ring and
  HW stops asserting IRQ.
