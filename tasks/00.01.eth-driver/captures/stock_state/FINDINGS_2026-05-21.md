# Stock TM Register Dump — Session 2026-05-21

## Method

Used `/dev/mem` via stock's `devmem2` in shell loop (`dumpregs.sh`). Stock is
running normally. Dumped 4 KB of TM region (phys 0x92340000..0x92340FFF).

## Key finding: 4 replicated TM instances

The same set of register values appears at offsets 0x000, 0x400, 0x800, 0xC00
within the TM block. Each instance is 0x400 = 1 KiB.

### Per-instance values (each of the 4 instances is identical at init)

```
+0x000  TM_master_config       = 0x140
+0x004  ?                      = 0x10
+0x0E8  desc_base[0]           = 0x4E700000   ← DMA-physical
+0x0EC  desc_base[1]           = 0x4E710000
+0x0F0  desc_base[TX]          = 0x4FF1F000   ← PonTmRegTable[4] (we knew)
+0x0F4  desc_base[3]           = 0x4EC20000
+0x0F8  desc_base[4]           = 0x4FE20000
+0x0FC  BP_SIZE config         = 0x28000900   ← BP_SIZE=0x900=2304 (we knew)
+0x104  mask?                  = 0xFFFFFFFC
+0x124  ?                      = 0x03FFFFFF
+0x12C  IRQ mask               = 0x00001FFF
+0x134  ?                      = 0x001FFFFF
```

### Replication pattern

```
0x92340000..0x923403FF  TM instance 0  (probably LAN0 or PON RX)
0x92340400..0x923407FF  TM instance 1
0x92340800..0x92340BFF  TM instance 2
0x92340C00..0x92340FFF  TM instance 3
```

ALL FOUR have identical init values. Stock programmed all 4.

## Implication for mainline 6.6 driver

Our mainline `zx279128-eth.c` writes to TM register space at base offset 0
(i.e. only instance 0). If TX uses one of the OTHER 3 instances we never
programmed → packets enqueue but never emit on the wire.

**Action:** loop instance 0..3 in driver init, write each TM register to ALL
four instances (offsets 0x000, 0x400, 0x800, 0xC00).

## PP block (0x92380000) — also has replication

Same dump method, 4 KB at PP base. Key findings:

### Replication detected at +0x400

Marker `0x242F0` appears at offsets `+0x904` and `+0xD04` (delta 0x400):

```
PP[0x904] = 0x242F0    PP[0xD04] = 0x242F0
PP[0x908] = 0x64       PP[0xD08] = 0x64
PP[0x90C] = 0x411      PP[0xD0C] = 0x411
PP[0x910] = 0x22008E3F PP[0xD10] = 0x22008E3F
PP[0x914] = 0xC7000007 PP[0xD14] = 0xC7000007
PP[0x918] = 0xF000107C PP[0xD18] = 0xF000107C
```

So PP has at least 2 instances at +0x900 and +0xD00. Likely 4 instances total
just like TM, but only instances 1 and 3 (or 0 and 1) shown above; we need to
dump 0x800-0x900 and 0xC00-0xD00 to confirm.

### PP scheduler block at 0x92380C00

Dense block of values from 0xC00-0xCE0 — looks like queue scheduler config:
- 0xC00=0x1, 0xC04=0x2ABFC8D, 0xC08=0x1, 0xC0C=0x640064
- 0xC10=0x1, 0xC20=0xFFF, 0xC24=0x106, 0xC28=0x1070104
- 0xC90=0x3AA, 0xC94=0x7F, 0xC9C=0xBA00
- 0xCA0=0xC3, 0xCA4=0xC3BA00
- 0xCC0..0xCDC = 8-entry packet rule table (each entry has 0x1C304BA / 0x1C30000 pattern)

This is the SchRegTable / QmgRegTable we suspected was missing (task #91)!
Stock has it programmed; our mainline driver likely does not.

## PP — confirmed 4 instances at +0x100/+0x500/+0x900/+0xD00
